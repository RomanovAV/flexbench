# FlexBench: бенчмарк типовых задач разработки

## Цель

На **рабочей машине** изучи репозитории в `~/Development` и `~/IdeaProjects` и на их основе **создай работающий переиспользуемый бенчмарк** в проекте `flexbench`.

Он должен позволять:

1. Запускать одни и те же типовые задачи на **GigaCode** и **GigaFlex** и сравнивать качество, время и расход ресурсов.
2. Повторять оценку после изменения rules, системного промпта, модели или настроек одного исполнителя.
3. Видеть по каждой задаче улучшения, регрессии и причины неудач.

Результат — набор задач, воспроизводимые исходные состояния, независимые проверки, скрипты запуска и отчёты. Документация сопровождает реализацию. Используй Python, shell и существующие тестовые инструменты, когда это упрощает работу. Не ограничивайся планом эксперимента.

OpenSpec — используемый процесс Spec-Driven Development. Он входит в задачи там, где это соответствует реальной работе. Сравниваемые исполнители — GigaCode и GigaFlex. Не требуй OpenSpec для каждой задачи и не делай его отдельным исполнителем.

Рабочие репозитории ещё не изучены. Одноимённые каталоги личного ноутбука не являются источником. Не предполагай интерфейсы инструментов, их архитектуру и доступные модели без проверки.

## 1. Исследовать проекты и выбрать задачи

Прочитай применимые инструкции и проверь существующие изменения. Начни с обзора; приложенный скрипт помогает получить локальную инвентаризацию:

```bash
python3 scripts/inventory_repositories.py \
  --root ~/Development --root ~/IdeaProjects \
  --output artifacts/repository-inventory.json
```

Скрипт не запускает модели и код проектов. Он собирает Git-метаданные, имена файлов конфигурации и статистику расширений. Это указатель для дальнейшего чтения, а не анализ архитектуры. При отсутствии каталогов или ошибках в отчёте сначала уточни соответствующие пути/доступ. Отчёт хранить внутри рабочего контура: в нём есть внутренние пути и темы коммитов.

Различай репозитории инструментов и продуктов. Первые нужны, чтобы разобраться в запуске и конфигурации GigaCode/GigaFlex/OpenSpec. Вторые — основной источник задач разработки.

Изучи README, релевантные исходники, тесты, CI, OpenSpec-артефакты и историю изменений. Составь `docs/discovery.md`: репозиторий, стек, архитектурные части, команды проверок, типы работы и источники выводов. После обзора выбери репрезентативные проекты для глубокого изучения; одинаково глубокий аудит всех каталогов не нужен.

Собери кандидаты из реальных изменений: дефекты, бизнес-валидация, API и клиент, работа с БД, рефакторинг, тестирование, конфигурация/сборка. Это направления поиска, а не заранее утверждённый набор. Для каждой выбранной задачи укажи конкретный исходный модуль/историческое изменение и объясни типичность. Частоту и трудоёмкость отмечай как измеренные либо предположительные.

Не выбирай задачи по ожидаемой победе GigaFlex. Включи простую работу, где накладные расходы инструмента могут оказаться неоправданными, и сложную — если она действительно встречается в проектах.

## 2. Построить fixtures и независимую приёмку

Начни с **2–3 полностью воспроизводимых задач** и доведи их до сквозного отчёта. Затем расширь MVP примерно до 8–12 задач применимых классов и сложности. Это ориентир объёма, не гарантия статистической мощности.

Для каждой задачи подготовь:

- Стабильный ID, версию, категорию и происхождение.
- Постановку: нужное поведение, ограничения и доступные материалы. Для автоматического режима она должна быть достаточной без ручных подсказок.
- Исходный snapshot/commit, зависимости, данные и процедуру подготовки.
- Видимые команды проверки для исполнителя и отдельные независимые критерии приёмки.
- Проверки нового поведения, граничных случаев и существенных регрессий.

Исторические изменения можно использовать для восстановления задач и контрольного решения. Не передавай исполнителю готовые патчи, будущие коммиты с решением или закрытые проверки. Изолированный snapshot должен исключать доступ к ним через Git-историю. Для компактной производной fixture объясни сохранённые и упрощённые свойства реального проекта.

Оценивай поведение, а не совпадение с эталонным diff, число строк или коммитов. Структуру решения проверяй только при наличии соответствующего требования.

Реализуй валидируемый manifest. Пример полей, не готовая конфигурация:

```yaml
id: repository_feature_001
version: 1
suite: dev
category: validation
source: {repository: REQUIRED, revision: REQUIRED}
fixture: {ref: REQUIRED, digest: REQUIRED}
prompt: task.md
setup: REQUIRED
visible_checks: []
grader: REQUIRED
requirements: []
default_limits: {wall_seconds: REQUIRED}
```

В реальных manifests все обязательные значения должны быть заполнены. Изменение постановки, fixture или grader создаёт новую версию. Исходный проект должен воспроизводимо собираться; известные исходные ошибки фиксируются отдельно.

Проверь сам grader: исходное состояние проваливает новое требование, контрольное корректное решение проходит, несколько ошибочных решений отклоняются. Например, пропуск граничного случая или отключение видимого теста не должны приводить к ложному успеху. Контрольные решения хранятся отдельно от среды исполнителя.

Закрытые проверки и grader должны быть недоступны исполнителю на чтение и изменение. Соседняя папка сама по себе не обеспечивает изоляцию: используй доступный sandbox/container или явно укажи ограничение. Приёмка выполняется после остановки исполнителя, без возврата закрытых результатов в его контекст. Новые тесты, написанные агентом, не заменяют независимую приёмку.

## 3. Реализовать скрипты запуска и адаптеры

Выбери минимальный стек по существующему проекту. Если оснований для другого нет, используй Python CLI с небольшим числом зависимостей. Автоматизируй цепочку:

```text
задача + профиль + параметры эксперимента
  → чистое окружение из fixture
  → применение выбранных rules/prompt/settings
  → GigaCode или GigaFlex
  → остановка и сохранение результата
  → независимая приёмка
  → запись метрик и сравнение с baseline
```

Выясни реальные интерфейсы инструментов: CLI/headless/API, передачу задачи и модели, применение rules и системного промпта, логи, usage, exit codes и остановку. Не выдумывай флаги. Реализуй два адаптера с общим контрактом. Если headless-режима нет, поддержи ручной импорт результата и явно укажи, какая часть пока не автоматизирована.

Runner должен уметь:

- Валидировать задачи/профили и проверять окружение без вызова модели.
- Выбирать suite, case IDs, профиль, модель и число повторов.
- Создавать независимые окружения, сбрасывать историю/память и изменяемые данные между запусками.
- Ограничивать время внешним тайм-аутом и останавливать дочерние процессы. Поддержать доступные лимиты расхода; ограничения, которые технически не обеспечиваются, явно обозначить.
- Собирать usage всех ролей, повторов и ревью GigaFlex, patch/итоговые файлы, stdout/stderr, события и статусы.
- Запускать независимую приёмку и сохранять структурированный результат.
- Присваивать уникальные run IDs; продолжать batch без перезаписи результатов, скрытых повторов и признания прерванного запуска успешным.
- Строить отчёт по эксперименту и сравнивать два experiment IDs.

Не сбрасывай исходные рабочие checkout через reset/clean. Используй отдельные копии, фиксированные зависимости и воспроизводимые сервисы. Rules/settings применяй только к изолированному запуску, сохраняя глобальную конфигурацию пользователя.

## 4. Отделить задачи от конфигураций

Раздели задачи, адаптеры и **профили исполнителей**. Новая версия rules или промпта должна означать новый профиль, а не изменение задач или runner.

Профиль содержит инструмент и версию, модель/deployment, параметры генерации, rules, системный промпт или поддерживаемые overlays, workflow options, доступные инструменты и лимиты. Сохраняй snapshots/digests реально применённых настроек без секретов; одного пути к изменяемому файлу недостаточно.

Проверь приоритеты глобальных инструкций, repository rules, overrides и встроенного промпта. Недоступную для чтения/изменения часть обозначь и зафиксируй версию инструмента. Пользовательский текст не называй заменой системного промпта. Неподдерживаемый параметр нельзя молча игнорировать.

Подготовь определения таких экспериментов:

| Что проверяем | Baseline | Candidate | Что фиксируем |
|---|---|---|---|
| Исполнитель | GigaCode | GigaFlex | Задачи, модель при возможности, среда, лимиты |
| Rules | GigaCode + rules v1 | GigaCode + rules v2 | Всё, кроме rules |
| Промпт | GigaFlex + prompt v1 | GigaFlex + prompt v2 | Всё, кроме поддерживаемого prompt override |
| Модель | Инструмент + модель A | Тот же инструмент + модель B | Задачи и остальные настройки |

Если изменяются несколько параметров, называй результат сравнением конфигураций целиком. Если в GigaFlex разные модели выполняют разные роли, учитывай их все и не приписывай весь эффект инструменту.

Для каждого результата сохраняй: suite/task/grader versions, fixture digest, executor version, profile/config digest, model/settings, environment version, repeat/order, timestamps, лимиты, причину остановки, результаты каждого требования, usage, стоимость при наличии, ссылки на артефакты.

Сравнение исторических запусков должно проверять совместимость задач, graders, окружения и лимитов. Несопоставимые результаты показывай с причинами. Поддержи свежий парный baseline/candidate, чтобы уменьшить влияние дрейфа модели и загрузки сервера. Чередуй порядок профилей, фиксируй условия кэша и параллельность.

## 5. Проверить инфраструктуру benchmark

На тестовом адаптере без LLM проверь: корректный и ошибочный результат, тайм-аут, ненулевой exit, отсутствие инструмента, сбой grader, прерывание и продолжение batch. Убедись в отсутствии ложных успехов, потери результатов и загрязнения следующего запуска. Эти проверки доказывают работу runner, а не качество GigaCode/GigaFlex.

Затем проведи реальный сквозной smoke каждого доступного адаптера в пределах указанного оператором бюджета. Если доступа/бюджета нет, закончи независимый код и проверки, подготовь точные команды и обозначь непроверенную часть. Не заявляй адаптер полностью проверенным по mock-тестам.

## 6. Метрики и отчёт

Основная метрика — доля запусков, прошедших все обязательные требования в пределах бюджета. Сохраняй исход каждого требования для диагностики; частичный балл не заменяет общую приёмку.

Дополнительно: elapsed time, длительность независимой проверки отдельно, входные/выходные/кэшированные токены, usage всех ролей, стоимость при известных тарифах, вызовы/retries, регрессии и необходимость человека. Неизмеренные значения — null с объяснением. Ручное исправление помечает запуск как assisted и не превращает его в автономный успех.

Разделяй причину остановки исполнителя и результат приёмки. Exit code 0 не равен успеху; тайм-аут и сбой grader не равны проваленному функциональному требованию. Сохраняй все попытки; инфраструктурные сбои показывай отдельно и в общей работоспособности процесса. Повтор после сбоя — новая запись со ссылкой на исходную.

Отчёт сравнения показывает:

- Долю успеха и её изменение в процентных пунктах, число задач и повторов.
- Задачи, которые стали проходить или перестали проходить, и конкретные требования.
- Время и расход по задачам/категориям, включая неудачные попытки.
- Стоимость принятой задачи: расходы всех попыток / число принятых; при нуле принятых не определена.
- Diff конфигураций и ограничения сопоставимости.

Не ранжируй по времени только успешных запусков без доли успеха. Для малого набора показывай парные исходы и неопределённость. Если строишь интервалы, группируй повторы по задачам, сохраняя пары baseline/candidate: повторы одной задачи не заменяют новые независимые задачи. Не смешивай разные модели в одну оценку эффекта tools/rules.

## 7. Регулярная проверка rules и промптов

Раздели задачи на `dev` для итераций и `holdout` для проверки выбранной конфигурации. Почти одинаковые задачи и варианты одного бага должны быть в одной части. Smoke проверяет запуск и не является оценкой эффективности.

Цикл использования:

1. Зафиксировать baseline и версию suite.
2. Сформулировать гипотезу об изменении rules/промпта.
3. Создать candidate profile с одним изменением.
4. Запустить оба профиля на dev в одинаковых условиях с независимыми повторами.
5. Проверить улучшения, регрессии и расход; выбрать конфигурацию.
6. Подтвердить её на holdout, который не использовали при настройке.

Не менять требования ради прохождения candidate. Исправление grader создаёт новую версию и требует переоценки результатов обеих сторон; изменение задания или среды требует новых запусков. Переоценка старого patch не измеряет эффект нового промпта.

Если ошибки holdout использованы для следующей настройки, он больше не независимый: переведи раскрытые случаи в dev и пополни holdout новыми семействами. Постоянный regression suite защищает от известных ошибок и не заменяет свежую проверку обобщения.

## 8. Артефакты и готовность

Адаптируй структуру к репозиторию; ориентир:

```text
README.md                  # установка и проверенные команды
docs/discovery.md          # изученные проекты и выбор задач
cases/                     # постановки, manifests, версии
fixtures/                  # подготовка начального состояния
graders/                   # независимая приёмка, вне среды агента
profiles/                  # исполнители и варианты настроек
experiments/               # определения сравнений и лимиты
src/ или scripts/          # runner, adapters, отчёты
tests/                     # проверки инфраструктуры
artifacts/                 # локальные результаты, вне Git
```

В README дай реальные команды для инвентаризации, валидации cases, одного запуска, suite, сравнения профилей и добавления задачи. Укажи prerequisites, cwd, выходные файлы и exit codes. Реализуй выбранный CLI; не выдавай пример вымышленного интерфейса за готовые команды.

MVP готов, когда задачи привязаны к изученным проектам, fixtures воспроизводимы, graders проверены, хотя бы 2–3 задачи прошли сквозной путь и начальный набор наполнен. Runner изолирует повторы, сохраняет результаты, сравнивает профили и показывает регрессии. Rules/поддерживаемый prompt меняются без изменения задач. Реальная проверка обоих адаптеров подтверждена либо явно перечислена как незавершённая часть.

Полный модельный прогон можно выполнить позже внутри корпорации. Сейчас закончи весь доступный код, fixtures и проверки. Первичные прогоны базовых моделей помогут диагностировать сложность задач и ограничения среды, но не должны отбирать набор исключительно по преимуществу GigaFlex.

Гемба затем может использовать результаты и трассы FlexBench для разбора работы команды. Её организацию не включай в обязательный объём реализации benchmark.
