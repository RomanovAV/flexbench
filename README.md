# FlexBench

Первая исполняемая итерация бенчмарка для GigaCode/GigaFlex и сравнения конфигураций. Python 3.9+, Git, Node.js и Java JDK 17+; macOS/Linux. Python-зависимостей нет.

Сейчас доступны три автономные задачи, подготовленные по сценариям из присланного обзора рабочих проектов. **Это приближённые задачи для отладки измерений, а не воспроизведение корпоративных изменений и не готовый рейтинг инструментов.**

| ID | Задание | Что проверяется |
|---|---|---|
| `java-nearest-activity` | Найти ближайшую запланированную активность | Фильтрация, время, граничные случаи, неизменность входа |
| `js-retry-state` | Исправить повтор операции в UI | Переходы состояния, устаревшие ответы, повторные клики |
| `maven-version-alignment` | Согласовать обновление зависимостей в модулях | POM, наследование версии, сохранение остальных зависимостей |

Java-fixture не проверяет Spring/БД, JS-fixture не проверяет React/отрисовку. Maven-fixture использует вымышленные координаты; зависимости не скачиваются, совместимость библиотек не измеряется. Все три относятся к открытому dev-набору.

## Прогон текущей конфигурации

Для одного профиля baseline/candidate не нужны:

```bash
python3 -m flexbench run --profile profiles/gigacode-command.json --open-progress --output artifacts/current
```

Готовый профиль `gigacode-command.json` **запускает GigaCode автоматически**, проверяет результат и создаёт отчёт. GigaCode должен быть установлен, доступен в `PATH` и заранее авторизован на этой машине. `model: null` использует текущие настройки CLI; конкретную модель можно задать в профиле. Версия CLI определяется автоматически через `gigacode --version`. Если executable имеет другое имя/путь, укажите `executable` в профиле.

По умолчанию выбираются все задачи, один повтор. Можно указать несколько ID и число повторов:

```bash
python3 -m flexbench run --profile profiles/gigacode-command.json \
  --case js-retry-state maven-version-alignment --repeat 2 --output artifacts/current
```

С ручным профилем (`profiles/gigacode-manual.json` или `profiles/gigaflex-manual.json`) команда создаёт отдельную папку `manual-…` с независимыми workspace и `RUNBOOK.md`: выполнить задачи, при наличии импортировать измерения, оценить каждую попытку и построить отчёт готовой командой. Сам исполнитель в этом режиме не запускается. Автоматический адаптер GigaFlex ещё не подключён.

С настроенным command-профилем та же команда запускает исполнителя, показывает прогресс `[N/total]`, оценивает каждую попытку и **автоматически создаёт `report.md` и `summary.json`** в новой папке `report-…` внутри output. Отчёт включает только попытки этого вызова, даже при повторном использовании output. Неуспешные попытки тоже попадают в отчёт; код выхода остаётся `1`, если хотя бы одна неуспешна.

## Прогресс в браузере

Для любого автоматического прогона создаётся локальная страница; её адрес `Progress: file:///…/index.html` печатается до запуска исполнителя. `--open-progress` открывает её в браузере по умолчанию. Без этого флага можно самостоятельно открыть напечатанный файл. Сервер, порт и установка веб-зависимостей не нужны.

Страница обновляется каждые 2 секунды: завершённые попытки, успехи/ошибки, общее время, текущая модель/задача/повтор, этап подготовки/исполнения/grader, число событий и вызовов инструментов. GigaCode-события читаются во время работы процесса; после завершения добавляются итоговые токены и ссылки на отчёты. Для generic command-профилей видны этапы и время, но внутренние события инструмента не разбираются. Процент означает долю завершённых попыток; точный процент готовности ответа модели неизвестен.

В папке страницы сохраняется `progress.json` с текущим состоянием. Файлы страницы и JSON заменяются атомарно, поэтому браузер не читает наполовину записанную версию. После завершения автоматическое обновление прекращается, итоговая страница остаётся на диске. При Ctrl+C страница показывает прерывание, CLI возвращает `130`; сохранённые попытки остаются для разбора. Автоматического возобновления прогона нет. Сырой текст модели, команды и результаты инструментов на страницу не попадают.

## Один набор задач на нескольких моделях

Укажите точные ID моделей из вашей установки GigaCode. В примере `SECOND_MODEL_ID` нужно заменить на существующую модель:

```bash
python3 -m flexbench run \
  --profile profiles/gigacode-command.json \
  --models GLM-5.3-Flash SECOND_MODEL_ID \
  --case all --repeat 2 --open-progress \
  --output artifacts/models
```

Три задачи × два повтора × две модели = 12 отдельных попыток. Модели выполняются последовательно; для каждой задачи/повтора порядок моделей циклически меняется. Каждая попытка получает новый workspace, каждой модели передаётся `--model`. Настройки профиля и дополнительные инструкции фиксируются перед запуском и не перечитываются между попытками. Поддерживается и одна модель через `--models MODEL_ID`. Повторяющиеся ID отклоняются. Сейчас `--models` поддерживается для native-адаптера GigaCode.

В новой папке `artifacts/models/matrix-…` будут:

| Путь | Содержимое |
|---|---|
| `progress/index.html` | Общий прогресс всех моделей в браузере |
| `progress/progress.json` | Текущее состояние и список запланированных/завершённых попыток |
| `model-01/`, `model-02/`, … | Результаты попыток каждой модели; директории не зависят от символов в ID |
| `report/report.md` | Общая таблица качества, времени, токенов и стоимости по моделям и задачам |
| `report/summary.json` | Самодостаточная сводка `kind: "model_matrix"`, включая подробные данные каждой модели |
| `report/model-01/`, … | Обычные подробные отчёты по каждой модели |

Заданная модель и модели, сообщённые GigaCode, показаны отдельно. Если CLI использовал alias/fallback или не сообщил модель, сводка предупреждает об этом. API-ошибка одной модели не отменяет остальные попытки; отчёт включает неудачные результаты и возвращается код `1`. Техническая ошибка самого runner/подготовки останавливает прогон с сохранением текущего состояния и кодом `2`.

Для разной стоимости моделей добавьте `pricing_by_model` в профиль: это объект `{ "MODEL_ID": { ...pricing... } }`, где каждая запись имеет те же поля, что `pricing` ниже. При выборе модели используется её тариф. Общий `pricing` не переносится на другую модель: без подходящего тарифа стоимость неизвестна. Для обычного single-run структура результатов и команда `compare` сохраняются; например, можно сравнить `matrix-…/model-01` и `matrix-…/model-02`.

## Данные автоматического запуска

Адаптер GigaCode использует тот же subprocess-контракт, что соседний проект GigaFlex: `--approval-mode=auto-edit --allowed-tools run_shell_command --output-format stream-json -p <задание>`. Все опции стоят перед prompt. Это разрешает правки и shell-проверки в задании без диалога; stdin закрыт, сеанс не возобновляется. Настройки самого CLI и корпоративные ограничения продолжают действовать. Ошибка approval или API, включая ошибку при exit code 0, сохраняется как техническая остановка. Детали и источник контракта: `docs/GIGACODE_ADAPTER.md`.

Время измеряется runner; токены берутся из единственного финального события `result.usage`, модели и длительности CLI — из событий сеанса. При тайм-ауте до итогового события usage остаётся неизвестным. Встроенного тарифа нет: чтобы получить стоимость, добавьте реальный `pricing` в профиль по разделу ниже. Полные stdout-события сохраняются в `executor.jsonl`, stderr — в `executor.log`. Эти локальные файлы могут содержать код и ответы исполнителя, в сводный отчёт их текст не включается.

Отчёт для уже оценённых результатов одного профиля:

```bash
python3 -m flexbench report --runs artifacts/current/MANUAL_BATCH_OR_RUN_DIR \
  --output artifacts/current-report
```

`--runs` принимает папку с попытками, папку одной попытки или `result.json`. Укажите фактический путь, напечатанный командой. Незавершённые попытки в выбранной папке блокируют отчёт; результаты разных профилей или версий одной задачи не смешиваются. Существующая папка отчёта не перезаписывается.

Отчёт содержит долю успеха и причины остановки, суммарное/медианное время исполнителя, входные/выходные/кешированные токены, расходы по валютам, стоимость успешной попытки и метрики каждого запуска. JSON также содержит сводки по задачам и результаты отдельных проверок. Формат `summary.json` — версия 2; старые `result.json` с неизвестными метриками поддерживаются.

Стоимость успешной попытки = **стоимость всех попыток, включая неудачные / число успешных попыток**. При нуле успехов, неполных расходах или разных валютах она неизвестна. Полная сумма показывается только при полном покрытии; известная часть и число измеренных попыток выводятся отдельно. Отсутствующие данные не заменяются нулями. Время command-run не включает подготовку и grader; ручное время неизвестно.

## Первый прогон на рабочей машине

Из корня проекта:

```bash
python3 -m flexbench validate
python3 -m flexbench pilot
```

Вторая команда создаст **шесть отдельных Git-проектов**: три задачи для GigaCode и те же три для GigaFlex. Она напечатает путь к `RUNBOOK.md` с порядком действий и готовыми командами проверки.

Для каждого пункта открой указанную workspace в новом сеансе нужного инструмента и передай: «Выполни TASK.md в этой рабочей папке. Не читай файлы вне неё». После завершения останови исполнителя и выполни приведённую в runbook команду `grade`. Затем — команду `compare` в конце runbook. Модели этот CLI сам не запускает в ручном режиме.

До подготовки пилота заполни `model` и `executor_version` в профилях фактическими значениями. Сам runner не подтверждает настройки внешнего интерактивного инструмента: используй одинаковую модель и настройки с обеих сторон, если это поддерживается. При null отчёт явно предупреждает о неизвестной конфигурации.

Каждое окружение содержит исходную fixture и `TASK.md`; закрытые проверки и контрольные решения туда не копируются. Но **trusted-local режим не создаёт границу безопасности**: инструмент с доступом к родительскому каталогу способен увидеть graders и контрольные решения. Для независимой оценки на рабочей машине ограничьте доступ исполнителя его workspace средствами инструмента/контейнера. При отсутствии такого ограничения результаты остаются открытым отладочным пилотом.

## Сравнить вариант инструкций

```bash
python3 -m flexbench pilot \
  --baseline profiles/gigacode-manual.json \
  --candidate profiles/gigacode-boundaries-manual.json
```

Candidate добавляет `rules/boundaries.md` в `TASK.md`. Содержимое сохраняется в записи запуска. **Это пользовательские дополнительные инструкции**, а не автоматически настроенные native rules GigaCode и не замена системного промпта. Чтобы измерять именно native rules/system prompt, нужно подключить проверенный механизм конфигурации инструмента и фиксировать фактически применённое содержимое. Сейчас такого адаптера нет.

После настройки на этих задачах используйте новые задачи для независимого подтверждения. Три случая и один повтор помогают отладить процесс, но не подтверждают устойчивое преимущество.

## Один случай и автоматизация

```bash
python3 -m flexbench prepare \
  --case java-nearest-activity \
  --profile profiles/gigacode-manual.json \
  --output artifacts/baseline
```

После работы исполнителя:

```bash
python3 -m flexbench grade --run artifacts/baseline/ACTUAL_RUN_ID
```

`ACTUAL_RUN_ID` замените на путь, напечатанный `prepare`. В результатах будут отдельные проверки, причина остановки, snapshot итоговых файлов, patch и версии входов. Готовый результат не перезаписывается; следующая попытка создаётся заново. Прерванный command-run оставляется для разбора и не засчитывается; автоматического возобновления исполнителя в MVP нет.

Для GigaCode используйте готовый `profiles/gigacode-command.json`: дополнительный wrapper не требуется. Для другого headless-инструмента создайте generic-профиль **без поля `adapter`**, установите `mode: "command"` и заполните `command` **проверенным argv-массивом** запуска. Runner подставляет `{workspace}`, `{task_file}` и `{measurements_file}`, запускает команду с cwd=workspace, без shell и с закрытым stdin. Прочие фигурные скобки не обрабатываются. Исполнитель должен сам читать переданный task-файл; интеграция зависит от его реального CLI.

```bash
python3 -m flexbench run \
  --case all --profile profiles/YOUR_VERIFIED_COMMAND_PROFILE.json \
  --repeat 2 --output artifacts/command-baseline
```

Этот профиль нужно создать перед командой. Автоматический режим измеряет прошедшее время и ограничивает процесс с потомками по `timeout_seconds`. Не делайте `command` строкой с shell-операторами. При `launch_error`, ненулевом exit или timeout результат не становится успехом даже при прохождении части проверок.

## Токены и стоимость

Runner принимает единый JSON от адаптера исполнителя. Адаптер должен агрегировать **все обращения за одну попытку**, включая повторные запросы и обращения внутренних агентов, если они входят в оцениваемый запуск. Готовый адаптер GigaCode сам преобразует итоговый `result.usage` в этот формат. Промежуточные message.usage не суммируются с итогом. Для других generic-исполнителей нужен экспорт или wrapper; универсального парсинга текстовых логов нет.

В автоматическом режиме передайте wrapper путь `{measurements_file}` через argv. Это `measurements.json` вне workspace. Wrapper записывает туда итоговый JSON до завершения процесса; runner считывает и сохраняет нормализованные метрики сразу после остановки исполнителя. Для промежуточных измерений используйте `complete: false` и атомарную замену файла. Тайм-аут/ненулевой exit не удаляет доступные измерения. Ошибочный или отсутствующий JSON даёт предупреждение и неизвестные метрики, но не отменяет функциональную оценку.

Пример формата (числа демонстрационные):

```json
{
  "schema_version": 1,
  "source": "executor session usage export",
  "complete": true,
  "usage": {
    "input_tokens": 1000,
    "output_tokens": 100,
    "cached_input_tokens": 200
  },
  "cost": {"amount": 0.0025, "currency": "USD"}
}
```

`input_tokens` **включает** `cached_input_tokens`; суммарные токены вычисляются как input + output. Если передан `total_tokens`, он должен совпадать с этой суммой. Input/output — обязательные неотрицательные целые, когда есть `usage`; кеш можно опустить, тогда он неизвестен. `usage` и `cost` допускаются по отдельности. `complete` обязателен и относится ко всей записи: `true` означает полные данные за попытку, `false` — только известную часть. Измерения считаются сообщёнными адаптером/оператором, а не независимо проверенными биллинговыми данными.

Для ручного сеанса перед `grade`:

```bash
python3 -m flexbench attach-metrics --run RUN_PATH --file SESSION_METRICS.json
```

Импорт проверяет формат и сохраняет копию. Повторный импорт и изменение после `grade` запрещены. Для автоматического запуска метрики поступают только через файл адаптера, ручной импорт запрещён.

Если исполнитель не возвращает стоимость, можно добавить `pricing` в JSON профиля. **Это вымышленный пример структуры, не действующий тариф:**

```json
"pricing": {
  "currency": "USD",
  "source": "example tariff; replace with actual source and date",
  "input_per_million": 2,
  "cached_input_per_million": 0.5,
  "output_per_million": 8
}
```

Все три ставки обязательны. Формула: `((input − cached) × input_rate + cached × cached_rate + output × output_rate) / 1 000 000`. Тариф сохраняется вместе с результатом; оценка помечается `estimated`. Стоимость из экспорта generic-адаптера имеет приоритет и помечается `reported`. Если кеш неизвестен, а ставки обычного и кешированного input различаются, стоимость не рассчитывается. При нескольких моделях/тарифах внутри попытки generic-wrapper должен передать агрегированную стоимость, а не применять одну ставку ко всем обращениям. Адаптер GigaCode отказывается применять один тариф при нескольких сообщённых моделях или несовпадении сообщённой модели с заданной. Дополнительные расходы инструментов включайте в сообщённую стоимость, если они относятся к выбранной границе измерения; оценка по токенам их не учитывает.

Отчёт сохраняет источник и полноту метрик, метод расчёта, тариф и SHA-256 исходного файла измерений. `source` — короткая метка экспорта или тарифа: она попадает в отчёт, поэтому не помещайте в неё секреты или сырой лог. Валюты не складываются и не конвертируются. Сбор токенов/стоимости не устанавливает ограничений по этим бюджетам.

## Сравнение

```bash
python3 -m flexbench compare \
  --baseline artifacts/baseline \
  --candidate artifacts/candidate
```

Пути должны содержать результаты одного профиля с каждой стороны. Отчёт JSON показывает долю успеха, изменение в процентных пунктах, каждый критерий, причины ошибок, diff профилей и сводки эффективности обеих сторон. Проверяется совпадение набора задач, graders/fixtures, среды, лимитов и числа повторов. Незавершённые попытки не исключаются молча — сравнение просит их разобрать. В ручном режиме время исполнителя и успех в пределах бюджета неизвестны. Usage и стоимость доступны при наличии измерений; покрытие указывается отдельно. Результаты не следует интерпретировать как причинный эффект правил при изменении модели или других параметров.

Коды выхода: `0` — команда выполнена / оценка пройдена; `1` — оценка или выполнение задачи неуспешны; `2` — ошибка подготовки, аргументов или несовместимое сравнение. `compare` возвращает 0 при корректном построении отчёта даже при регрессии: автоматический порог допуска в MVP не задан.

## Как фиксировать результаты для поиска улучшений

После `grade` в папке каждого запуска сохраняются:

| Артефакт | Что даёт для разбора |
|---|---|
| `result.json` | Статус, критерии приёмки, версии задачи/профиля, модель, длительность command-run, usage/стоимость и полнота измерений |
| `measurements.json` | Исходный экспорт токенов/стоимости от адаптера или оператора, если доступен |
| `candidate/`, `changes.patch` | Итоговые файлы и изменения; новые неотслеживаемые файлы есть в snapshot, но могут отсутствовать в patch |
| `grader.log` | Ошибки компиляции/загрузки и результаты независимых проверок |
| `executor.log` | stdout/stderr автоматического исполнителя, если используется command adapter |
| `executor.jsonl` | Полный поток событий GigaCode; при native-адаптере `executor.log` содержит только stderr |
| `session.log` | Приложенный оператором журнал ручного сеанса |
| `observations.jsonl` | Сообщённые оператором вмешательства, препятствия, проверки и другие наблюдения |

В ручном режиме **перед `grade`** приложи экспорт доступного журнала и короткие наблюдения. Примеры команд (замени RUN_PATH и SESSION_LOG на реальные пути):

```bash
python3 -m flexbench attach-log --run RUN_PATH --file SESSION_LOG
python3 -m flexbench observe --run RUN_PATH --kind human_intervention \
  --text "Помог запустить тесты; код вручную не менял"
python3 -m flexbench observe --run RUN_PATH --kind intervention_summary \
  --text "Всего одно вмешательство: настройка запуска тестов"
```

Эти тексты — примеры, запиши фактические события. Если вмешательств не было, явно укажи это в `intervention_summary`; отсутствие записей считается неизвестным. Нужны видимые действия, команды, ошибки и ответы инструмента; скрытые рассуждения не требуются. `observe` также принимает `verification`, `obstacle`, `context_loss`, `executor_claim`, `note`. Такие записи считаются сообщениями оператора, не автоматически подтверждёнными фактами. История обычного чата не выгружается сама.

После оценки данные запечатаны: дополнительные наблюдения/логи этой командой уже не принимаются. Прохождение проверок при ручной помощи остаётся фактом приёмки, но не доказательством автономности. Сводная доля успеха включает все оценённые попытки; сведения о помощи показываются отдельно.

После завершения обеих сторон:

```bash
python3 -m flexbench report \
  --baseline artifacts/baseline --candidate artifacts/candidate \
  --output artifacts/report-01
```

Получатся `report.md` для чтения и `summary.json` для совместного анализа. В новом `pilot` точная команда уже будет в runbook. Отчёт группирует симптомы (границы, состояния, согласованность файлов, сохранение поведения, сборка/запуск), ссылается на run_id и проверки, предлагает **непроверенные гипотезы** и следующий эксперимент. Он не делает вывод о причине по одному факту провала теста. Если журнала или конфигурации не хватает, это указано явно.

Для обсуждения результатов передай `report.md` и `summary.json`. Они не содержат код, сырые промпты, CLI-команды, полные журналы или текст заметок; содержат идентификаторы запусков, модели/версии, результаты и метаданные. Если для проверки гипотезы нужен контекст, отдельно разбираем соответствующий diff и фрагмент журнала в разрешённом контуре.

Цикл улучшения: повторяющийся симптом → проверка по журналу/diff → одна гипотеза → один изменённый профиль → парный повторный прогон → проверка новых регрессий и подтверждение на новых задачах. Например, провал `stale_result` даёт основание проверить обработку устаревших ответов, но сам по себе не доказывает, что нужно менять системный промпт.

## Проверка самого бенчмарка

```bash
python3 -m unittest discover -s tests -v
```

Проверяются исходные неверные решения, контрольные корректные решения, частичные исправления, тайм-ауты, независимость workspace и неизменность сохранённых результатов. Контрольные решения в `tests/reference_solutions.py` предназначены только для проверки graders; не передавайте их испытуемому агенту.

## Материалы и развитие

- `docs/PILOT_DESIGN.md` — границы пилота, источники сценариев, следующий шаг.
- `GIGAFLEX_BENCHMARK_INSTRUCTIONS.md` — расширенная инструкция для разработки полного бенчмарка внутри рабочего контура.
- `scripts/inventory_repositories.py` — инвентаризация Git-проектов. Для актуальной рабочей выборки укажите её корни через повторяемый `--root`, а не все исторические checkout.
- `artifacts/` — локальные отчёты и запуски, исключены из Git.

Первое расширение: проверить адаптер GigaCode на установленной целевой версии, заменить одну приближённую fixture реальным snapshot до изменения и подтвердить контрольное решение. Расширять обследование всех репозиториев перед этим не требуется.
