# Автоматический адаптер GigaCode

```bash
git pull --ff-only
python3 -m flexbench run --profile profiles/gigacode-command.json --open-progress --output artifacts/gigacode-auto
```

Команды выполняются из корня FlexBench на машине с установленным и авторизованным GigaCode. Прогон автоматически создаёт workspace каждой задачи, запускает GigaCode, выполняет grader и сохраняет общий `report.md` / `summary.json`. Ручной runbook не создаётся. Для первого короткого прогона можно добавить `--case maven-version-alignment`.

Прогресс доступен в локальном `index.html`, который автоматически обновляется в браузере; `--open-progress` открывает его. Для одинакового прогона на нескольких моделях добавьте `--models MODEL_A MODEL_B` с реальными ID. Результаты разделяются по моделям и сводятся в общий `model_matrix`-отчёт. Подробности структуры и `pricing_by_model` приведены в README.

## Источник контракта

Интерфейс сопоставлен с `gigacode --help`, присланным с целевой машины 2026-10-19, и существующим проектом GigaFlex (локальный checkout `gigalphex`, чистая рабочая копия, commit `8f0b0dc1b722b63dc53891900569aac0a964f5fd`):

- `python/gigaflex/defaults.py` — approval и разрешённый shell-инструмент;
- `python/gigaflex/executor.py`, `_with_stream_json_output` — формат потока и расположение prompt;
- тот же файл, `_StreamJsonDecoder`, `_parse_usage`, `_models_from_stats` — итоговый usage и метаданные сеанса;
- `tests/test_executor.py`, `test_stream_json_extracts_text_usage_and_timings`, `test_marks_api_error_as_failure_when_process_exits_zero` — примеры событий и ошибок;
- `README.md` и `docs/gigacode-approval-diagnostic-20260622.md` — причина использования `-p`, отдельное разрешение shell-команд и историческая проверка версии 26.5.17.

GigaFlex не импортируется и не устанавливается как зависимость FlexBench. Используется его контракт внешнего процесса. На машине разработки FlexBench GigaCode отсутствует; автоматические тесты используют исполняемый fake CLI и реальные fixture/grader. Реальный запуск с моделью должен быть подтверждён на целевой машине.

## Запуск и настройки

Фактический argv:

```text
gigacode --approval-mode=auto-edit --allowed-tools run_shell_command --output-format stream-json [--model MODEL] -p TASK_CONTENT
```

`TASK_CONTENT` — один аргумент с полным содержимым подготовленного `TASK.md`, включая дополнительные инструкции профиля. Все флаги передаются до `-p`. cwd — workspace конкретной попытки; stdin закрыт. `--continue`, `--resume`, `--worktree` и `--safe-mode` не добавляются. Обычные настройки/контекст CLI продолжают действовать, так что это измерение текущей конфигурации, а не гарантия отсутствия глобальной памяти. Изоляция оценщика не обеспечивается.

`model: null` оставляет выбор модели GigaCode. Непустая строка передаётся через `--model`. Версия определяется через `--version`; фактически сообщённые модели сохраняются отдельно от заданного поля профиля. Не добавляйте `command` в профиль с `adapter: "gigacode"`: argv строит адаптер. Можно изменить `executable`, `timeout_seconds`, `instruction_files`, `approval_mode`, `allowed_tools` и добавить `pricing`.

Разрешение `run_shell_command` взято из GigaFlex: одного `auto-edit` недостаточно для тестов через shell. Если установленная версия отвергает этот флаг или корпоративная политика требует подтверждения, ошибка и stderr будут сохранены. Адаптер не переключает режимы approval автоматически и не повторяет модельные вызовы при ошибках.

## Usage и отчёт

В `executor.jsonl` сохраняется stdout с полным потоком событий; `executor.log` содержит stderr. Текст этих файлов в общий отчёт не экспортируется. Сохраняются их хеши. События `system`, `assistant` и `result` используются для метаданных; единственное финальное событие `result` определяет usage:

| Поле GigaCode | Поле FlexBench |
|---|---|
| `result.usage.input_tokens` | `usage.input_tokens` |
| `result.usage.output_tokens` | `usage.output_tokens` |
| `result.usage.cache_read_input_tokens` | `usage.cached_input_tokens` |
| `result.usage.total_tokens` | проверка суммы input + output; при отсутствии сумма вычисляется |
| `result.stats.models` | список фактически сообщённых моделей |
| `result.duration_ms` / `duration_api_ms` | длительности, сообщённые CLI, отдельно от времени runner |

Под `result` в таблице понимается событие с `type: "result"`, а не вложенное поле с текстом ответа. Input включает кеш: это согласуется с контрактом GigaFlex, где input=10, output=2, cache=3, total=12. Кеш повторно не прибавляется. Отсутствующий кеш остаётся неизвестным; отсутствующие или некорректные usage не обнуляются.

Usage промежуточных сообщений не складывается: иначе можно повторно посчитать уже включённые обращения. Без единственного финального события полный usage неизвестен. При неоднозначном потоке или отсутствии финального события завершившийся с кодом 0 процесс считается технической ошибкой. Тайм-аут и ненулевой exit сохраняют свою причину остановки. Если процесс успел выдать итоговый usage, он сохраняется даже для неуспешной попытки; при тайм-ауте помечается частичным.

Структурированная ошибка или отдельный ответ `[API Error: ...]` не считается успехом при exit code 0, даже если файлы проходят grader. Ошибка approval также выделяется отдельно. Реальные tool outputs/ответы не используются как инструкции runner.

В изученном контракте GigaFlex денежной стоимости нет. FlexBench рассчитывает её только по явно заданному реальному тарифу `pricing` (формат в README). При нескольких моделях или несовпадении модели с заданной одна ставка не применяется. Без тарифа стоимость остаётся неизвестной. Новые прогоны создаются отдельно: ранее запечатанные ручные результаты не изменяются.
