# Первая итерация FlexBench

Историческое описание исходных трёх задач. Текущий dev-набор расширен до восьми; происхождение пяти новых сценариев и добавленные условия перечислены в [CASE_SOURCES.md](CASE_SOURCES.md). Автоматический GigaCode, токены, каталог моделей, последовательный прогон и страница прогресса уже проверены пользователем на целевой машине; новые пять задач проверены локально на контрольных решениях, модельного прогона на них ещё не было.

## Решение

Начать с работающего короткого цикла, а не расширять инвентаризацию. Присланные inventory v2, discovery и bench-examples достаточны для выбора классов работы. Исходники корпоративных проектов в пакете отсутствуют, поэтому текущие fixtures написаны заново и обозначены `synthetic-derived`.

Три случая покрывают сервисную бизнес-логику, frontend-состояние и обслуживание зависимостей. Они не выражают доли загрузки команды. Новая инвентаризация содержит 178 checkout, из которых в 150 отмечены Java-файлы; это не означает, что 150/178 рабочего времени тратится на Java. Обновление одной зависимости в десятках сервисов может представлять одну кампанию изменений.

## Происхождение и добавленные условия

| Случай | Что есть в присланном обзоре | Что спроектировано здесь |
|---|---|---|
| java-nearest-activity | Архивное изменение выбора ближайшей запланированной активности | Java API, правило границы now, tie-break, обработка null, конкретные тестовые данные |
| js-retry-state | История изменений retry receipts и статусов UI | Чистый JS reducer, requestId, защита от устаревших ответов, конкретный контракт состояний |
| maven-version-alignment | Повторяющиеся обновления зависимостей многомодульных Maven-сервисов | Вымышленные библиотеки/версии, два POM, набор структурных ограничений |

Добавленные условия не выдаются за требования исходных продуктов. Ни один реальный fix не воспроизведён по одному заголовку commit. Выводы Explore/DeepSeek использованы как ориентиры; команды сборки корпоративных проектов здесь не запускались.

## Что можно проверить сейчас

- Подготовку одинакового исходного состояния для разных исполнителей.
- Способность решать эти конкретные небольшие задачи.
- Чувствительность оценки к пропущенным требованиям и частичным исправлениям.
- Пробное изменение дополнительных пользовательских инструкций и сохранение их версии.
- Исполняемый путь command adapter на тестовых процессах: timeout, exit code, артефакты и отчёт.
- Прогон одного профиля с выбором задач/повторов: runbook для manual, автоматический отчёт для command.
- Импорт токенов/стоимости через JSON-контракт адаптера или оператора, расчёт по сохранённому тарифу, сводки с явной полнотой измерений.
- Автоматический адаптер GigaCode: subprocess-контракт и stream-json взяты из существующего GigaFlex; запуск, сбор финального usage и отчёт проверяются fake CLI. Реальный модельный прогон требует целевой машины.

Что ещё не измеряется: фактическая эффективность GigaCode/GigaFlex без реальных прогонов, изменение native rules/system prompt, Spring/React/БД-интеграции, защищённый holdout, производственная пропускная способность. Native-адаптер GigaCode получает финальный usage; для GigaFlex пока нужен ручной импорт. Денежная стоимость требует реального тарифа или явного экспорта биллинга. Локальная среда не изолирует оценщик от агента с доступом к диску.

## Первый рабочий прогон

Одинаковые модели и ограничения, новые сеансы, без ручного исправления итогового кода. Изначально `pilot` создавал 3 × 2 = 6 задач-попыток; теперь он выбирает весь набор (8 × 2 = 16). Одного повтора достаточно, чтобы найти проблемы запуска; для вывода об устойчивости нужны новые задачи и повторные измерения. Изменения инструкции пробуются на dev-наборе; после этого он не считается holdout.

Для первого настоящего replay на рабочей машине взять один исходный проект и одно изменение из исследования. Восстановить revision до изменения и проверить доступность зависимостей. Требования извлечь из самой спецификации, не заголовка. Контрольный patch держать вне workspace. Приёмка должна отвергать исходное поведение и принимать исправление. Не считать пустой Maven test run, отключённые тесты или успешный Sonar достаточной функциональной приёмкой.

## Оставшиеся этапы

1. Провести шесть ручных запусков и проверить понятность постановок/приёмки.
2. Проверить готовый GigaCode command-профиль на целевой версии; подключить автоматический адаптер GigaFlex. Проверить, как именно применяются rules, системный промпт и модель; хранить effective config.
3. Добавить одну реальную сервисную и одну реальную frontend-fixture, сохранив автономные случаи как smoke/dev.
4. Подтвердить полноту финального usage GigaCode реальным прогоном и подключить usage GigaFlex; добавить принудительные общие бюджеты, изоляцию оценщика, сохранение причины прерывания batch, пороги отчёта для CI и новый holdout.

Не расширять набор повторяющимися версиями одной задачи ради числа случаев. Не оценивать качество нового промпта по красоте самого промпта: оценивать решения задач, произведённые исполнителем с этой конфигурацией.
