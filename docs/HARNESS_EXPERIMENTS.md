# Эксперименты с конфигурацией харнесса

Цель — измерять влияние правил, промпта и настроек выполнения на одной модели.
Единица сравнения — baseline/candidate, а не название продукта. Текущие восемь
задач — открытый dev-набор для настройки; подтверждать выбранное улучшение нужно
на новых задачах, которые не использовались при доработке конфигурации.

## Первый эксперимент

В существующем UI выбор модели работает и для экспериментов:

```bash
source .venv/bin/activate
python -m flexbench harbor view
```

Откройте `http://127.0.0.1:8080/run`. В режиме **«Сравнение настроек харнесса»**
выберите эксперимент, одну модель из актуального каталога GigaCode, задачи и
повторы. Раскройте «Какие настройки сравниваются» для просмотра baseline/candidate.
Для пробного запуска достаточно `js-retry-state` и одного повтора: две попытки.
Кнопка «Запустить эксперимент» сохраняет входы и запускает отдельный worker.
Закрытие страницы не останавливает серию; остановка доступна в карточке запуска.

После завершения на странице видны результаты по конфигурациям и задачам, причины
неудач и ссылки на попытки в Harbor. Можно скачать Markdown, JSON и настройки
эксперимента. «Сохранённые эксперименты» возвращает к прошлым сериям, в том числе
после перезапуска сервера; сервер после перезапуска не получает право останавливать
процесс прежнего сервера. Повтор того же запроса после потери ответа не создаёт
второй эксперимент. Модель повторно проверяется по каталогу перед запуском.

Список экспериментов берётся из `experiments/*.json`. Другой каталог задаётся
при запуске сервера через `--experiments-dir PATH`. UI принимает только ID
опубликованной в этом каталоге спецификации; пути, команды и окружение через
форму не передаются. Профили обоих вариантов должны использовать тот же executable,
что профиль сервера (при необходимости задайте `--profile PATH`).

### CLI для автоматизации

На целевой машине с установленными Harbor и авторизованным GigaCode, из корня
репозитория. Выберите точный доступный ID через `python -m flexbench models`.
Замените `MODEL_ID` во всех командах одним и тем же ID.

```bash
source .venv/bin/activate
python -m flexbench models
python -m flexbench harbor experiment \
  --spec experiments/verify-contract.json --model MODEL_ID \
  --case js-retry-state --repeat 1 --dry-run
```

Dry-run проверяет CLI через `--version`, runtime, профили и конфигурации Harbor;
сохраняет снимок эксперимента, не отправляя задание модели. Доступность inference
этим не подтверждается. Чтобы проверить реальный путь, повторите команду без
`--dry-run`: это две новые попытки. Каждая команда создаёт новый каталог.

Полная серия — 8 задач × 2 конфигурации × 3 повтора = 48 попыток:

```bash
python -m flexbench harbor experiment \
  --spec experiments/verify-contract.json --model MODEL_ID
```

Baseline использует текущий профиль. Candidate добавляет только
`rules/verify-contract.md`: сопоставление требований с проверками, адресные тесты
для граничных случаев и завершение после проверки. Улучшение — проверяемая гипотеза,
не установленный эффект. Файл можно редактировать для следующего эксперимента;
уже созданные эксперименты продолжают использовать сохранённый текст.

## Что можно менять

Профили — JSON. `instruction_files` задаёт список файлов относительно профиля;
их тексты дописываются к заданию на пользовательском уровне. Необязательный
`prompt_prefix_file` заменяет вводную часть пользовательского запроса перед
заданием. Его содержимое также замораживается. Без него используется обычная
вводная часть адаптера. `approval_mode` и `allowed_tools` передаются существующими
флагами GigaCode; действующие корпоративные политики продолжают применяться.

Это **не подмена native system prompt** и не установка native rules. Подтверждённого
контракта этих механизмов пока нет. Неизвестные поля профиля в эксперименте
отклоняются, включая `system_prompt_file` и `native_rules`, чтобы не получить
сравнение молча проигнорированных настроек. Для подключения native-механизма нужны
проверенные `--help`/документация целевой версии и свидетельство применения.
Глобальные настройки CLI и серверная ревизия модели не фиксируются автоматически.

`version` в профиле — необязательная метка оператора; точная идентичность
определяется хешами содержимого. ID и пути файлов сами по себе не считаются
изменением поведения. Одинаковые по эффективным настройкам профили отклоняются.

Эксперимент требует одинаковые executable, версию CLI, модель, timeout и тариф.
Разные лимиты или модели — отдельные условия исследования, а не эффект rules.
Несколько изменённых полей допустимы и явно перечислены в отчёте; их совместный
эффект нельзя приписать одному полю. Модель задаётся явно через `--model` или
`model` в спецификации; противоречащая модель в профиле вызывает ошибку.

## Порядок и воспроизводимость

Спецификация содержит `schema_version: 1`, `name`, `hypothesis`, пути `baseline`
и `candidate`, `cases`, `repeat`, `seed`, необязательный `model`. Пути профилей
разрешаются относительно спецификации. `--case`, `--repeat`, `--model` позволяют
сузить пробный запуск; фактический план сохраняется в `experiment.json`.

Каждая пара «задача × повтор» выполняется рядом, последовательно; первый вариант
для каждой задачи меняется между повторами. Порядок задач перемешан фиксированным
seed. При нечётном числе повторов один вариант идёт первым на один раз чаще.
Seed управляет только расписанием, не случайностью модели. Параллельность равна 1
для всего эксперимента; автоматических retries нет. Каждая попытка — отдельный
job Harbor, отдельный Git workspace и новый сеанс GigaCode.

Все задания, fixtures, graders, тексты профилей и job-конфигурации замораживаются
до первой попытки. Перед следующей попыткой проверяются их хеши. Изменения исходных
файлов после подготовки не влияют на замороженные входы. Это проверка целостности,
а не граница безопасности: локальный агент технически имеет доступ к соседним
каталогам. Не меняйте глобальные настройки GigaCode во время серии.

## Результаты и прерывание

Команда печатает каталог `artifacts/experiments/experiment-…/`:

- `experiment.json`: гипотеза, модель, профили, diff, версии задач/runtime, хеши и расписание.
- `profiles/`, `tasks/`, `configs/`: сохранённые входы.
- `jobs/attempt-…/`: результаты Harbor, проверки и журналы.
- `jobs/attempt-…/<trial>/agent/invocation.json`: фактически переданные argv и
  пользовательский prompt, его хеш и версия CLI. Это свидетельство отправки,
  не доказательство того, что модель выполнила инструкцию.
- `outcomes/`, `state.json`: состояние каждой запланированной попытки и серии.
- `summary.json`, `report.md`: сравнение, обновляемое после каждой попытки.

Отчёт показывает общий успех, функциональную приёмку, исходы по задачам и парам,
проваленные проверки, причины остановки и разницу candidate − baseline в процентных
пунктах. JSON содержит время всех попыток, токены и покрытие, расходы по валютам и
стоимость успешной попытки с учётом расходов неудачных попыток. Без тарифа стоимость
неизвестна. Расходы после тайм-аута могут быть неполными.

Незавершённые попытки не объявляются провалами; у неполной серии нет итоговой разницы.
Несовпадение/отсутствие сообщённой модели, версии CLI или свидетельства отправленного
промпта сохраняется как ограничение доказательств и блокирует итоговую разницу.
Функциональный успех после API-ошибки/тайм-аута не превращается в общий успех.
Ошибка запуска сохраняется отдельно, остальные попытки продолжаются.

После Ctrl+C сохраняются имеющиеся результаты и неполный отчёт. Повторного запуска
того же эксперимента нет: новая попытка требует нового каталога. Восстановить
производный отчёт из сохранённых файлов, без модели и повторной приёмки:

```bash
python -m flexbench harbor experiment-report \
  --experiment artifacts/experiments/experiment-YYYYMMDDTHHMMSS-ID
```

Коды `experiment`: 0 — все попытки успешны и сравнение подтверждено сохранёнными
данными; 1 — завершённое сравнение содержит неуспешные попытки; 2 — ошибка настройки,
неполное/неподтверждённое сравнение; 130 — прерывание. `experiment-report`: 0 для
полного подтверждённого сравнения, 1 для неполного/неподтверждённого, 2 при ошибке чтения.

Для CLI-эксперимента просмотр отдельных попыток через Harbor:

```bash
python -m flexbench harbor view \
  --output artifacts/experiments/experiment-YYYYMMDDTHHMMSS-ID
```

Для браузерных запусков эксперимент сохраняется в `<output>/experiments/experiment-…/`,
а его jobs — в общем `<output>/jobs/` с уникальным префиксом эксперимента. Их видит
история Harbor того же сервера. Сравнительная сводка находится в каталоге эксперимента.
CLI-каталоги не импортируются автоматически в браузерную историю экспериментов.
Три повтора дают первичный сигнал повторяемости;
они не заменяют новые независимые задачи и не доказывают универсальное улучшение.
