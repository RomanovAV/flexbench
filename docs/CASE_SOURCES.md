# Происхождение расширенного dev-набора

Пять новых задач выбраны по ранее присланному анализу рабочих репозиториев. Они написаны заново: в пакете есть обзоры, Git-метаданные и ссылки на изменения, но нет исходников, полных production-spec и контрольных патчей. `synthetic-derived` означает производный сценарий, а не восстановленный реальный fix. Имена классов, API, примеры, ошибки, ограничения и критерии приёмки спроектированы для FlexBench и не выдаются за требования команды.

Первоначальные три задачи и их graders не меняются. Их происхождение описано в `PILOT_DESIGN.md`.

## Независимая приёмка

Для каждой fixture заданы `task.md`, исходный `fixture/`, видимая smoke-команда и отдельный Python-grader в `graders/`. Java-grader компилирует решение вместе со своим harness в отдельной временной папке. JS-grader использует управляемые Promise: порядок запуска и заполнение свободного слота проверяются без сравнения скорости моделей. Таймер служит только защитой от зависшего решения. SQL-grader создаёт настоящую in-memory БД, сравнивает данные и ответы до/после миграции, проверяет EXPLAIN без automatic_index и сортировки во временной B-tree. Для SQL в runtime записывается версия SQLite. Grader упаковки запускает `/bin/sh` с stub java, проверяет argv, PID после exec и код выхода.

`tests/test_expanded_cases.py` проверяет всю цепочку prepare → snapshot → grade → result: исходные решения отклоняются содержательно, контрольные решения проходят, видимые smoke-команды также проходят на контрольных решениях. По четыре частичных/ошибочных решения на задачу отклоняются конкретными проверками: права/повтор/данные/overflow; версия/граница/quota/составной ключ; concurrency/rejection/dedup/status; порядок индекса/partial index/unique/удаление данных; несогласованный образ/quoting/heap/exec. Контрольные решения находятся только в `tests/expanded_solutions.py` и в workspace исполнителю не копируются.

Режим trusted-local по-прежнему не создаёт защищённого holdout: соседние graders и контрольные решения не изолированы от процесса с доступом ко всему диску. Число задач выросло с 3 до 8, но фактическую сложность новых задач и различия моделей ещё требуется измерить на целевой машине. Прохождение тестов устанавливает только выполнение записанных контрактов; читаемость/архитектура автоматически не оцениваются.

Следующий шаг к реалистичности — на корпоративной машине получить исходный snapshot и полную спецификацию одного из перечисленных изменений, восстановить сборку и доказать, что независимая приёмка отвергает исходник и принимает реальный fix. Этот пакет не подменяет такой replay.

## Изменение приёмки рекомендаций: версия 2

После разбора первого модельного прогона выявлен пропуск в grader версии 1: реализация могла обрезать пробелы составного ключа вопреки явному требованию буквального сравнения и при этом пройти существующие проверки. Это установлено дополнительными примерами на восстановленном решении, а не выводом из одного значения pass rate.

Версия 2 сохраняет постановку, исходную fixture и контрольное решение. Изменяется только независимая приёмка:

- общий `skip_invalid_candidates` заменён пятью проверками: null-кандидат, id, taskType, source и null dueAt;
- проверяются несовпадение ключей с разными пробелами/регистром, допустимость отдельных правил с такими ключами и отдельная дедупликация id `"x"` / `" x "`;
- теперь 24 проверки с учётом компиляции вместо прежних 17;
- регрессионные проверки отвергают удаление проверки пробельного id, нормализацию составных ключей и id, потерю защиты от null-кандидата и null dueAt. Ошибка остаётся провалом содержательного критерия, а не ошибкой компиляции;
- отчёт поддерживает новые диагностические IDs, а прежний ID сохранён для чтения исторических результатов.

Manifest version увеличена до 2, fingerprint задачи/grader изменён. Сохранённые результаты v1 не переоцениваются и не смешиваются с v2. Для нового парного сравнения обе модели выполняют свежие попытки с прежними параметрами профиля. Изменение grader не доказывает улучшение модели; оно повышает покрытие уже записанного контракта.
